# 优化路线

矩阵乘的全部难度只有一句话:**算得少、搬得多**。`2MNK` 次乘加对应 `(MK+KN+MN)` 个元素,K 越大,每个搬进来的字节就该被用得越多次。下面每一级都是在提高「一个字节被用几次」,直到把 tensor core 喂饱。

每一级后面标了它在**体检单**里对应哪个指标 —— 改完去看那一行有没有动,这是唯一可靠的验证方式。

> **这条路线走的是每种语言官方推荐的路,不是从零手搓。** 官方教手写的(合并访存、分块、双缓冲、
> Ampere 的 WMMA)就手写;官方自己都不推荐手写的(Hopper 之后的 wgmma / tcgen05 协议)就用它给的封装。
> 一级的价值在于让你**看见某个旋钮动了之后数字怎么变**,不在于它写起来多难。
>
> 下面每一级的数字都是实测的。**有几级是不升反降的**,那不是笔误 —— 那几级往往最值钱。

## 0. 朴素:每个线程算一个 C 元素

```
for k in range(K):
    acc += A[m, k] * B[k, n]
```

`A` 的一行被 `N` 个线程各读一遍,`B` 的一列被 `M` 个线程各读一遍。算术强度只有 **0.25 flop/B**,离 roofline 拐点(5090 上约 128)差三个数量级。

**体检单**:判定「卡在搬数据上」,显存接近 100%,tensor core 是 0。

## 1. 合并访存 (memory coalescing)

同一个 warp 的 32 个线程如果访问的是连续地址,硬件把它们合成几个 128 B 的事务;如果是跨行的跳跃地址,就退化成 32 次独立事务,带宽直接掉到 1/32。

判断方法:让 `threadIdx.x` 走**最内层连续维**(行优先时是列)。写成 `C[ty][tx]` 而不是 `C[tx][ty]`。

**体检单**:L1/TEX 的「每请求 sector 数」。合并良好是 4,退化后会接近 32。

## 2. 共享内存分块 (tiling)

把 `A` 的 `BLOCK_M × BLOCK_K` 和 `B` 的 `BLOCK_K × BLOCK_N` 搬进共享内存,块内复用。每个元素被复用 `BLOCK_N`(或 `BLOCK_M`)次,算术强度提高同样的倍数。

```
        B tile
      ┌──────────┐
      │ BK × BN  │
      └──────────┘
 A tile      ↓
┌────────┐ ┌──────────┐
│ BM × BK│→│  C tile  │  一个 CTA 负责一块 C,沿 K 一段一段累加
└────────┘ └──────────┘
```

分块大小的天花板是共享内存:**5090(sm_120)每 block 上限 101376 字节**。`BLOCK_M×BLOCK_K + BLOCK_K×BLOCK_N` 个元素 × 元素字节 × 流水级数,超了就编不过。

**体检单**:L2 命中率上去、显存那行下来;「共享内存 / block」那一行是你算的那个数。

## 3. 寄存器分块 (thread tiling)

共享内存也有带宽上限。让每个线程算 `TM × TN` 个输出而不是 1 个,把复用再往上提一层到寄存器 —— 共享内存读一次,寄存器里用 `TM × TN` 次。

代价是**寄存器压力**:累加器就占 `TM × TN` 个寄存器/线程。寄存器一多,每 SM 能并发的 block 就少,占用率掉下来。这是本级唯一的权衡。

**体检单**:「每个线程占几个寄存器」与「warp 位置用了多少」,尤其是后者的说明 —— 它会直接告诉你卡在寄存器还是共享内存上。

## 4. 多级流水 (cp.async / num_stages)

到这里计算和访存还是串的:搬完一块 → 算一块 → 再搬。用 Ampere 的 `cp.async` 把「搬下一块」和「算当前块」重叠起来,开 N 级缓冲就能掩盖 N-1 段的延迟。

Triton 里这就是 `num_stages`,编译器会自动降到 `cp.async` 多级缓冲。共享内存用量按级数翻倍,所以第 2 级的上限在这里会被重新触碰。

**体检单**:「等显存把数据取回来」的占比应该明显下降。用 `klab ptx` 能直接数出 `cp.async` 的条数确认它真的生成了。

## 5. Tensor core (mma.sync / tl.dot)

前面四级都在解决「喂得够不够快」,这一级换「算得够不够快」:用矩阵指令替代标量 FMA。Ampere 是 `mma.sync`(同步,warp 级),Hopper 是 `wgmma`(异步,warpgroup 级),数据中心 Blackwell 是 `tcgen05`。

Triton 里写 `tl.dot(a, b)` 就够,降到哪条指令由目标架构决定。**`klab ptx` 是唯一能确认这件事的工具** —— 体检单只说 tensor core 忙到几成,不说走的是哪条指令。

**体检单**:判定应该翻成「卡在算上」,tensor core ≥ 80%。到了这里主要等待变成「等计算单元排队」,那是好事,说明 tensor core 在排队等着干活。

## 6. L2 swizzle(program 重排)

默认 `pid → (pid_m, pid_n)` 是按行铺的,同时在跑的那一批 block 横跨了很宽的一条,它们需要的 `B` 列几乎没有交集,L2 白白浪费。改成**按 group 分组**(连续的 `GROUP_M` 行块聚成一团再铺),同批 block 就会共享 tile。

```
按行铺(差)            按 group 铺(好)
0  1  2  3  4  5       0  2  4  6  8  10
6  7  8  9  10 11      1  3  5  7  9  11
```

**体检单**:L2 命中率。这一级对大矩阵收益明显,对已经放得进 L2 的小矩阵基本没有。

## 6.5 split-K:块数不够时把 K 也切开

`(M/BLOCK_M) × (N/BLOCK_N)` 块要是比 SM 数还少,一多半 SM 从头空转。教科书答案是把 K 也切成若干段,并行度乘以 SPLIT_K,各段算部分和再累加。cuBLAS 遇到瘦长形状就这么干。

**但在 5090 上实测,这一级是输的**:1000×999×777 从 0.37× 掉到 0.33×(SPLIT_K=4)、0.20×(=8)、0.12×(=16),越切越慢。原因是用全局 `atomic_add` 累加部分和,原子流量把收益吃光了;cuBLAS 不走全局原子,它用 workspace 存部分和再跑一个规约 kernel。

**这个形状的真正修法是更小的分块**:autotune 给它选了 `BLOCK 64×64`,块数从 64 变成 256,不用 split-K 就填满了 SM,直接 1.23× 超过 cuBLAS。「块数不够就 split-K」是想当然 —— 先试更小的分块。

## 7. 尾波 (wave quantization)

一次能并发的 block 数 = `SM 数 × 每 SM 能放几个 block`。5090 有 170 个 SM,如果每 SM 放得下 2 个,一波就是 340 个。`4096/128 = 32×32 = 1024` 个 block,`1024 = 3×340 + 4` —— 最后一波只有 4 个 block 在跑,340 个槽位空了 336 个,整整浪费掉 1/4 波的时间。

改法:调分块让 block 数接近槽位数的整数倍,或者提高占用率让槽位变多。

**体检单**:「切成多少块」那行会直接告诉你最后一波用掉几成位置、浪费多少时间。注意 3.01 波比 3.98 波糟得多 —— 小数部分越小,尾波越空。

## 8. 换代:五种语言,四张卡,谁真的用上了新硬件

这一节全是实测,没有一个字是推测。把每种语言的基线代码**一个字不改**,拿 `klab ptx` 在四张卡上各打一遍:

| 语言 | 你写的那一句 | A100 sm_80 | 5090 sm_120 | H100 sm_90 | B200 sm_100 |
|---|---|---|---|---|---|
| **triton** | `tl.dot(a, b)` | `mma.sync` | `mma.sync` | **`wgmma`** | **`tcgen05`** |
| **tilelang** | `T.gemm(A, B, C)` | `mma.sync` | `mma.sync` + **TMA** | **`wgmma`+TMA+`setmaxnreg`** | `mma.sync` + TMA + `setmaxnreg` |
| **cuda** | `wmma::mma_sync(...)` | `wmma.mma` | `wmma.mma` | `wmma.mma` | `wmma.mma` |
| **tk** | `warp::mma_AB(...)` | `mma.sync` | `mma.sync` | `mma.sync` | `mma.sync` |

### 读这张表

**上面两行会换代,下面两行不会。** 区别只有一个:

- `tl.dot` / `T.gemm` 说的是**「把这两块乘起来」** —— 你没点名指令,编译器就挑目标卡上最好的那条。
- `wmma::mma_sync` / `warp::mma_AB` 说的是**「用这条指令」** —— 你点名了,编译器不能替你换。

所以那份 CUDA 代码放到 B200 上,四万美元的卡跑得像 A100。**这不是 bug,是你自己写的。**

### 三条更细的结论

1. **TileLang 在 H100 上自动用满了 Hopper**:`wgmma` + TMA + `setmaxnreg`(warp specialization,一部分 warp 专职搬数、一部分专职算)。三样新特性,零行代码。
2. **但 TileLang 在 B200 上没用 tcgen05**,退回了 `mma.sync` —— 而 Triton 3.8 在同一张卡上用上了。**「自动」也分成熟度**,而唯一能发现这件事的办法就是去量。
3. **5090 有 TMA 但没有 wgmma**(sm_120 不是 sm_90 的超集)。TileLang 在它上面用了 TMA,tensor core 却还是 `mma.sync`。

### 那「点名型」的语言怎么换代?

**换一个名字就行,不用重写。** 这几种语言都把每一代的协议细节打包好了,你只是挑一块积木:

| 语言 | Ampere | Hopper | 数据中心 Blackwell |
|---|---|---|---|
| **tk** | `warp::mma_AB` | `warpgroup::mma_AB` | `tcgen05::mma` |
| **cute** | `warp.MmaF16BF16Op` | `warpgroup.MmaF16BF16Op` | `tcgen05.MmaF16BF16Op` |
| **cuda** | `wmma::mma_sync` | *官方答案:改用 CUTLASS* | *同左* |

CuTe DSL 里这件事尤其干净:**同一个类名 `MmaF16BF16Op` 在三个命名空间里各有一份**,
`cutlass.cute.nvgpu.warp` / `warpgroup` / `tcgen05` 分别对应 Ampere / Hopper / 数据中心 Blackwell。
换代 = 换一行 import。**挑中它,发哪条指令、描述符怎么编码、数据怎么摆,全在这块积木里。**

(注意别被 C++ 版的命名带偏:CUTLASS 的 C++ CuTe 里 atom 叫 `SM90_64x128x16_F32BF16BF16_SS` 这种,
Python DSL 不用这套名字。本仓库走的是 Python DSL。)

裸 CUDA 到 Hopper 之后没有官方的手写封装(WMMA 只覆盖到 Ampere),NVIDIA 自己的答案就是「用 CUTLASS」。所以这个仓库里 **cuda 这一列到 Ampere 为止**,再往上是改 CUTLASS 的参数(tile 形状 / schedule / atom),或者直接走它的 Python 前端 —— 也就是本仓库 cute 这一列。**这本身就是一条该学的结论,不是我们偷懒。**

### 显式用某一代:见参考答案 `5-tma`

上面是「编译器替你换代」。想**显式**指定,Triton 给了 API(`tl.make_tensor_descriptor` 就是 TMA)。那一级实测出一件要紧的事:

**在 A100(没有 TMA 硬件)上,那份代码不报错、不变慢,它只是被静默降级成了普通 `cp.async`。**

代码照跑、结果照对,你完全看不出来。所以:

> **「我写了 TMA」和「硬件真的用了 TMA」是两件必须分开验的事。** 体检单只说 tensor core 忙到几成,不说走的是哪条指令 —— 这就是 `klab ptx` 存在的唯一理由。

## 9. 别自己猜:autotune

前面每一级都在手工拧常量,而实测一再打脸 —— swizzle 没用、提占用率没用、split-K 反而更慢。把候选列出来让编译器跑一遍,按形状分别记住最快的一组,才是可靠的收尾。

5090 实测 72 组候选:手写的 `128×128×32 / warps 4 / stages 3` 在三个形状上**没有一个是最优的**,而 autotune 三个形状全部追平或超过 cuBLAS。

这不是说前面几级白学 —— 你得先知道有哪些旋钮、每个旋钮动的是体检单哪一行,才能把候选列对,也才能看懂搜出来的结果为什么快。

## 到哪一级算够

看两个数就行:**相对 torch 的倍数**和**对峰值的百分比**。cuBLAS 是几十人年调出来的,能到 0.9× 已经说明前六级都做对了;超过 1.0× 通常意味着你利用了某个 cuBLAS 不知道的先验(固定形状、特殊 layout、能融合的后续算子)。

低于 0.5× 的话,别急着往下一级走 —— 先用体检单的判定 + `klab ptx` 找出卡在第几级。
