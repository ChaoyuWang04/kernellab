# 决策记录

> 这里放**为什么**。核心指引文档只写结论,理由、背景、当时的权衡一律记在这里。
> 需要改变某条守则时,先来看它当初为什么那么定。

---

## D1. 这个仓库学的是「优化」,不是「手搓」

**决定**:每种语言走它**官方推荐**的路。阶梯 = 逐级打开优化旋钮与硬件特性,不是逐级手搓更多底层。

**用户原话(定调的那一段)**:

> 我不是想成为一个算子的大神级别的人物,手写一切。我想说的只是我甚至连一个算子都还没有亲自手写过,
> 所以我们都按照官方推荐的来准备我的学习材料就好,不用硬写最难的。这对于所有的语言所有的特性都是如此。
> 我只是想感受一下手写算子的不同优化,然后修改不同的硬件特性什么的。
> 这是一个学习为主的仓库 —— **学习如何写出一个优化到工业级的算子,而不是从零手搓出一个工业级别的算子。**

**这条原则不等于「一律用 CUTLASS」。** 这是最容易误解的一点,所以写死在这里:

判定方法只有一句话 —— **问「官方文档在这一格推荐什么」,照做**。答案经常就是手写:

| 这一格 | 官方推荐 | 我们就 |
|---|---|---|
| 合并访存 / 共享内存分块 / 寄存器分块 / 双缓冲 | 手写(CUDA 编程指南就是这么教的) | **手写** |
| Ampere 的 tensor core | `nvcuda::wmma`(NVIDIA 自己的封装) | **用 WMMA** |
| Hopper / Blackwell 的 tensor core(裸 CUDA) | **没有官方手写封装**,NVIDIA 的答案是 CUTLASS | 改 CUTLASS 的参数 |
| ThunderKittens 换代 | 换命名空间(`warp::` → `warpgroup::` → `tcgen05::`) | 换名字 |
| CuTe 换代 | 换 atom(`SM80_*` → `SM90_*` → `SM100_*`) | 换积木 |
| Triton / TileLang 换代 | 什么都不用做,编译器按目标卡选指令 | **代码不动,去量** |

**这条原则的实际效果,是救活了一个格子,不是废掉已有的。** 旧假设「每种语言都从零手搓到工业级」下,「裸 CUDA × Hopper」被判成「太难,不做」;新原则下它变成「该做,而且不难 —— 改的是参数,不是指令」。

**它排除掉的东西非常具体**:手写 `wgmma` / `tcgen05` 的 PTX 协议、手写 `mma.sync` + `ldmatrix` 的 fragment 布局。除此之外的手写都是合规的,而且是这个仓库的主要内容。

**推论**:难度不是价值。一级的价值在于它让用户**感受到某个旋钮动了之后数字怎么变**,不在于它写起来多难。

## D2. 三层分离:代码 / 环境 / 后端

**决定**:代码住在 Mac(本仓库,git 管理);环境定义在仓库里(`envs/<工具链>/`);后端只回答「在哪跑」(`targets.toml`)。

**理由**:GPU 是租来的、借来的、会丢的。远端不保存任何不能从 Mac 重建的状态,机器没了重跑一次 `klab setup` 就回来了。加新功能时先问它属于哪一层,能避免绝大多数结构性错误。

---

## D3. Target 接口只有四个方法

**决定**:`sync / run / fetch / shell`,不许加第五个。编译、测速、NCU、扫参全是 `run()` 之上的命令串。

**理由**:后端可插拔的唯一前提。往接口里加一个方法,每个后端都要实现一遍,加第三个后端时就会塌。命令串放在 CLI 层,所有后端自动同时获得新能力。

---

## D4. spec 契约与 DSL 无关

**决定**:只有 `make_inputs / run / reference / workload`(可选 `configure`)。harness 不认识任何 DSL。

**理由**:五种语言(以后可能更多)共用一套跑法、一套体检单、一套对比表,数字才能横着比。DSL 的差异被挤到两个地方:`toolchains/<name>.py`(怎么装)与 `spec.py`(怎么调)。

**推论**:`reference()` 必须用**与算子相同 dtype** 的原生 torch 调用,不许先 `.float()`。它既是 check 的基准,也是 bench「相对 torch」标尺的来源 —— 先 `.float()` 会把 GEMM 变成 fp32、多一次拷贝,标尺直接虚高(matmul 曾因此显示 11× 快于 torch,修正后是 0.9×)。

---

## D5. 文件即数据,不引数据库、不引 web 框架

**决定**:`runs/<id>/result.json` 是唯一的结果真源。体检单、对比表、基线、面板全从它推导。面板服务端是 stdlib `http.server`,前端无构建。

**理由**:这是个人实验台,不是产品。数据库会带来迁移、备份、schema 演进三件事,而 `runs/` 目录用 `rm -rf` 就能清空、用 `git log` 就能追溯。面板引 web 框架会带来 node 运行时与构建步骤,而它要做的事只有「读文件、渲染、fork 子进程」。

**约束**:面板不许有自己的持久化状态 —— 所有它显示的东西必须在文件系统里能找到源头。

---

## D6. 不做 `--target auto`

**决定**:后端一律 `--target` 显式选,不给就用 `targets.toml` 的 `[defaults] target`。

**理由**(用户 2026-09-18 决定):算子还少,手选不烦;自动匹配会引入「为什么它选了这张卡」的调试成本。等算子多到手选变烦再加。

---

## D7. `kernels/<名>/` 是用户的

**决定**:那个目录里只有算子源码,agent 不改、不加文件,除非用户明确要求。接线一律放 `specs/<名>/`。

**理由**:用户要练的就是写算子本身。agent 一旦开始「顺手优化一下」,这个仓库的意义就没了。评价里可以引用它的行号,但不动它。

**踩过的教训**:有一次 agent 用 `git add -A` 把用户在面板里的改动扫进了一个无关的 commit。所以提交前必须先看 `git status`。

---

## D8. 参考答案的结论必须是实测的

**决定**:每一级 docstring 里的数字都来自真实运行。**不编造单调递增的阶梯** —— 没收益就如实写没收益,并解释为什么。

**理由**:这个仓库唯一的价值是「旋钮动了,数字怎么变」。编一条永远上升的曲线,等于把唯一的价值删掉。

**现实是曲线经常不升反降**,而这些反例恰恰是最值钱的几级:

- `cuda/2-smem`:加了共享内存分块,**慢了 10%** —— 分块本身不产生收益,产生收益的是复用;复用没提到寄存器那一层,就只是把瓶颈搬了个家。
- `cuda/4-doublebuf`:双缓冲,**持平** —— 到那一级瓶颈已经不是「等数据」,是标量 FMA 的吞吐。
- `triton/3-splitk`:split-K 在 1000×999×777 上从 0.37× 一路掉到 0.12× —— 全局 `atomic_add` 的原子流量把收益吃光了;这个形状的真正修法是**更小的分块**。
- `tilelang/1-swizzle`:没用。

## D9. `klab ptx` 是「换代」类答案的唯一证据

**决定**:凡是声称用上了某一代硬件特性的答案,必须用 `klab ptx` 验证指令真的换了。

**理由**:实测发现两件事,任何一件都能让「我写了 X」变成假的:

1. **Triton 的 TMA API 在 A100(没有 TMA 硬件)上会静默降级成普通 `cp.async`** —— 不报错、不变慢,代码照跑、结果照对,你完全看不出来。
2. **「自动」也分成熟度**:同一份 `T.gemm`,TileLang 0.1.14 在 H100 上用满了 `wgmma`+TMA+`setmaxnreg`,在 B200 上却退回了 `mma.sync`;而 Triton 3.8 在同一张 B200 上用上了 `tcgen05`。

体检单答不了这个问题 —— 它只说 tensor core 忙到几成,不说走的是哪条指令。

**判定只认标志指令**:`mma.sync` / `wmma.mma` / `cp.async`(Ampere)、`wgmma` / `cp.async.bulk`(Hopper)、`tcgen05`(数据中心 Blackwell)。`ldmatrix` / `stmatrix` / `mbarrier` / `setmaxnreg` 是辅助指令,只报条数不进判定 —— 它们「某代起就有」,5090 照样会发 `stmatrix`,出现了并不说明用上了那一代的核心能力。

## D10. cute 的 PTX 怎么取(2026-09-20 解决)

**决定**:五种工具链全接上了,取法各不相同。

**曾经的死路**:`JitFunctionArtifacts.PTX` 字段存在但填不上(打开 `DeviceTarget` 选项也是 `None`),`dump_to_object` 出来的是宿主 ELF,`cuobjdump` 抠不出来。一度记成「接不上」。

**真正的口子是环境变量**,藏在 `cutlass/base_dsl/env_manager.py`:

```bash
CUTE_DSL_KEEP=ptx          # 还可以是 cubin / sass / ir,逗号分隔
CUTE_DSL_DUMP_DIR=<目录>
```

**必须在 `import cutlass` 之前设**——env_manager 在导入时就把环境读进去了,之后再设没用。所以 `runner.py` 在 `spec.load_module()` 之前调 `ptxdump.prepare(spec)`,而不是在取 PTX 的时候才设。

**教训**:「上游没实现」和「上游的开关我没找到」是两回事。下次再遇到「这个工具链取不到 X」,先 `grep -rhoE '<PREFIX>_[A-Z_]+'` 把它的环境变量全列出来看一遍。

## D11. 版本不钉

**决定**:`envs/*/requirements.txt` 故意不钉版本,取最新。

**理由**:这个仓库有一半内容是在观察「编译器现在成熟到哪一步了」(见 D9)。钉死版本等于把这个观察窗口关上。

**代价与应对**:某次升级把某条工具链弄坏了,就在对应 `requirements.txt` 里钉住上一个可用版本,并在注释里写日期与原因。升级工具链后值得重跑一遍 `klab ptx` 的四卡对照 —— 上次就是这么发现 TileLang 在 B200 上还没用 tcgen05 的。
